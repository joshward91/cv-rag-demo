Harbour Help evaluation

Harbour Help is a grounded, retrieval-augmented help assistant for a small demo CRM. It answers only from the CRM's help centre: 29 short articles for signed-in customers (27 single-task how-tos that match the app screen for screen, a glossary and a note about the demo data), plus 15 overview pages for visitors who aren't signed in. It doesn't use the model's general knowledge, has no tools or web access, and cites the article behind every answer. Retrieval is hybrid: keyword search (BM25F) with a coverage-based decision policy, plus semantic search (sentence embeddings from all-MiniLM-L6-v2, run in the visitor's browser). Semantic search reads an HNSW vector index built ahead of time, the same kind of index pgvector or a vector database would use. It is designed to fail safe: when it isn't confident it asks or hands over to support instead of guessing.

To test retrieval under more realistic pressure, the evaluation also runs it inside a wider Harbour suite: 969 help articles for five sister products, and 190 documents the assistant must never show (internal staff material, drafts, archived articles and documents with no status) in the same vector index. Only documents whose status is public reach the assistant, and a visitor sees only the pages written for everyone.

ScreenAn input guard blocks obvious prompt injection (“ignore previous instructions”, role changes, prompt extraction, tag smuggling) before anything else runs.
Look upSigned in, a question about the account’s own records (“show me Priya’s phone number”, “open Deals worth more than 10k”) is answered straight from the data by a small deterministic parser, with no model call. Everything else goes on to help search.
RewriteThe question is normalised and rewritten with domain rules. The articles say "client" for the user's own business, so "a client's phone number" is read as a Contact's phone. Synonyms are mapped and typos corrected.
Retrieve (hybrid)Keyword: BM25F over title, aliases and body, weighted 3 : 2 : 1, plus a coverage score for how much of the question each article explains. Semantic: the rewritten question is embedded and its nearest article passages (titles, aliases and sentences, with sentences weighted ×0.9) are read from an HNSW index, filtered to the documents this viewer may see.
DecideA deterministic policy, so the decision is free and explainable. Answer when coverage is high. Ask when two look-alike articles are equally likely. Suggest up to three articles when only semantic search finds a close match. Otherwise hand over to support.
GenerateOffline, the article's own steps. With Claude, a schema-constrained reply that may cite only the articles in the prompt, with a note saying which "client" the user meant.
VerifyAny answer that cites none of the articles it was given, or contains a link, is withheld. Citations of articles it wasn't given are dropped.

This report measures every step on questions in seven sets. Four are held out from the code they test, and three of those have never been tuned on. It shows how often the assistant finds and cites the right article, asks when it should, and hands off what the help centre doesn't cover. It also compares Claude Haiku, Sonnet and Opus on cost per correct answer, measures the vector index against a flat scan, and runs two further blind sets: one across the Harbour suite and one asked both signed in and as a visitor.

Metrics by question set

The dev set was used to tune the retriever. The test set was scored blind once, then used for a second round of tuning. The hold-out set was written before that second round and never tuned on, so it is the honest estimate for questions the system hasn't seen. The perspective set tests "client" from both sides and was scored blind once before a final one-rule fix. The hard hold-out was written before semantic search was built: paraphrases that avoid the articles' wording, scored blind and never tuned on. The everyday voice set was written by a separate agent that saw only the articles: rambling, non-expert and deliberately ambiguous questions such as "I'm just on hold with a client and I can't figure out how to change their number". It was scored blind and never tuned on.

Keyword search alone vs keyword + semantic

Every question runs twice: once with keyword search only, once with semantic search added. Semantic search never answers on its own, so it barely moves the strict pass rate (here it didn't move at all). What changes is how often a user who would have been sent to support is offered the right article instead. The useful rate is measured over answerable questions only.

    Appendix: withheld documents deliberately published for evaluation

    These documents are published here on purpose. Every document has a status: draft (the default for new documents), public, internal or archived. Only public documents reach the assistant. These are the rest: internal staff training, runbooks and policies, unpublished drafts, archived articles for the old interface, and a few legacy documents with no status at all, which the same rule withholds as a safety net. They are listed so a reviewer can check that none of them ever appears in an answer, a suggestion or a prompt. In a real deployment they would not be public at all.
